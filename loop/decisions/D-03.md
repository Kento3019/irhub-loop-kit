# D-03 人の判断（2026-09-26、REJECT a1 の必須3件への対応方針）

1. 送信場所の食い違い：案(c)。`Hub::replaceSchedules` は一覧を入れ替えるだけで、送信も `lastScheduleMin_` の更新もしない。各分の判定は `Hub::tick` が判定した時点の一覧で決まる（分の変わり目から1秒以内に保存した場合は新しい一覧が使われる）。D-01 10節の決まり2（送信してよいのは applyAc / pressLight / tick の3か所）はそのまま守る。
2. ID 採番の順番：3.1 の手順を「検証 → 一覧を写す → 入力 id の最大値が nextId_ 以上なら nextId_ = 最大値+1（最大値が 9999 なら 1）→ id の無い件に採番（使用中の id は飛ばす）」とする。3.2 の例に「再起動直後 [5, 無] → [5, 6]、次は 7」と「最大 id 9999 のあとに1件足す」を加える。
3. JSON の id の範囲：schedule_json が uint16_t に詰める前に確かめる。整数でない（小数・文字列・真偽値・null）→ `schedules[i].id: must be integer`、1..9999 の外（0, -1, 10000, 70000）→ `schedules[i].id: out of range`、いずれも 400。id が無い件は採番。6.4 に文言を、テスト観点に 0 / -1 / 10000 / 70000 / 1.5 / "1" を足す。
